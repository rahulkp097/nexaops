# NexaOps — Build Plan

Source: `NexaOps_Complete_Project_Build_Documentation.docx`

## What this project is

A full-stack enterprise AI operations copilot:
- **Frontend**: Next.js chat UI, admin dashboard, eval/observability dashboards
- **Backend/API**: NestJS gateway (auth, RBAC, conversations, admin)
- **AI service**: FastAPI (RAG, tools, agent orchestration, NL-to-SQL, evaluation, observability)
- **Async worker**: document ingestion (extract → chunk → embed)
- **Mock business service**: fake operational APIs (customers/orders/inventory/revenue) for tool-calling demos
- **Infra**: PostgreSQL + pgvector, Redis, RabbitMQ, Docker Compose, deployment

Not backend-only — covers the whole system end to end.

Every bound the spec calls out is enforced: max tool calls and max iterations (hard counters), a wall-clock timeout budget (`asyncio.wait_for` per call against a shared deadline), a token budget (cumulative input+output tokens across the run), and an allowed-tool list (the model is never even offered a tool name outside its role — `registry.to_anthropic_tools()` gained a `role` filter for this). Once any budget is exhausted, or on the last allowed iteration, tools stop being offered at all rather than the loop ending abruptly — Anthropic cannot request a tool it wasn't offered, so this deterministically forces a coherent final text answer instead of a hard cutoff. Identical repeated `(tool, arguments)` calls within one run are served from a cache instead of re-executed. A bound being hit is a normal, structured `AgentRunResult.stopped_reason`, never an exception; a tool failure is fed back to the model as data (`{error, message}`) via a `tool_result` block, never raised into the loop. Spec §25's first two bullets — "store complete conversation messages" and "use a bounded recent-message window" — were already done by Phase 8 (the full `messages` table, plus `CONVERSATION_HISTORY_LIMIT = 10` forwarded as multi-turn history); this phase's actual new work is the third bullet, "summarize older context when conversations become long": `conversations` gained `summary`/`summarized_message_count` columns (`infra/database/migrations/..._add-conversation-summary-columns.js`), and a new `ConversationsService.maybeUpdateSummary` folds only the slice of messages that has just aged out of the 10-message window into a rolling summary — never the whole conversation, and never more than once per newly-aged-out slice — via a new `apps/ai-service` module (`app/memory/summarizer.py`, `POST /memory/summarize`). The resulting summary is threaded into both `app/rag` and `app/agents`' system prompts (both gained a `build_system_prompt(conversation_summary)`, replacing a bare constant for the agent side to match RAG's existing pattern) as a delimited `<conversation_summary>` block, given the same "context only, never instructions" framing Phase 15 established for retrieved evidence and tool output — summarization input is the user's own already-trusted conversation turns, not untrusted content, but the output still shouldn't be read as new instructions once it re-enters a system prompt. Summarization is deliberately a best-effort enhancement, not a dependency of chat working at all (spec §19's "graceful degradation when an optional AI dependency fails"): if the `/memory/summarize` call fails, `ConversationsService` logs a warning and falls back to the conversation's last-known summary rather than blocking the message from posting — relevant in practice today, since summarization sits behind the same Anthropic call already blocked by the account's zero-credit-balance gap. Spec §25's last two bullets ("keep user/organization identity outside conversation text", "do not let conversation memory override authorization") were already satisfied architecturally — `organization_id` has always been a parameter the server supplies, never a message field or something the model can set — audited rather than rebuilt, same as several of Phase 15's checklist items. `/agent/run` gained the identical `conversation_summary` parameter for consistency (both endpoints share the same `HistoryMessageDto` shape already), but this does not touch the still-open Phase 13 gap below — chat still only ever calls `/rag/query`/`/rag/query/stream`, never `/agent/run`. Next: Phase 17 — AI Evaluation. `evaluation_cases`/`evaluation_runs`/`evaluation_case_results` (spec §7) hold a fixed dataset — no CRUD API (spec §24's contract lists only run endpoints) — seeded by `scripts/seed-evaluation-dataset.mjs` against a real running stack (register/upload/poll for `READY`, then upsert case rows directly via Postgres, matched by organization+category+question so re-seeding never orphans past runs' results). `apps/ai-service/app/evaluation` executes each of the spec's 10 categories through the exact pipeline that would really answer it — `run_rag_query`'s constituent calls for `DOCUMENT_QA`/`NO_ANSWER`/`EXACT_ID`/`MULTI_HOP`/`PROMPT_INJECTION`, `run_agent` for `COMBINED`/`AGENT_MULTI_STEP`, and, deliberately bypassing the LLM's own tool/query selection entirely, `registry.execute()` directly for `BUSINESS_API`, the Phase 12 validator directly for `SQL`, and retrieval alone (no generation call at all) for `CROSS_TENANT` — so a third of the categories are fully live-scorable today regardless of account credits, since a WHERE clause, a validator, and a registered tool handler don't depend on model behavior. Every metric in `app/evaluation/scoring.py` (recall@K, citation accuracy, a faithfulness check against hallucinated `[n]` citation markers, answer correctness) is a cheap structural proxy rather than an LLM judge, documented as a proxy at each function — this project has never had a real answer to judge and "no paid AI service required for the local MVP" is a stated non-goal. For the RAG categories specifically, retrieval is scored *before* generation is attempted (a new decomposition of what `run_rag_query` normally does in one call), so `recallAtK`/`citationAccuracy` still get a real score even when the generation half fails — without this split, a genuine retrieval regression would be indistinguishable from the account's known billing gap. A single case's own pipeline error (LLM or otherwise) is folded into that case's structured result (`error` set, `passed: false`) and never raised — one bad case can't abort a run, same "never a raw exception" convention as `registry.execute()` and the Phase 13 agent loop. `apps/gateway/src/evaluation` owns the ADMIN-only public contract (`POST/GET /evaluation/runs`, `GET /evaluation/runs/:id`) as one synchronous request — every case already has its own bound (tool timeout, agent timeout budget), so the whole run is finite, and there's no reason to stream partial progress the way chat does. Live-verified end to end: seeded 15 cases (spanning all 10 categories, including a genuine second "canary" organization so `CROSS_TENANT` tests real tenant isolation, not a same-org proxy) against the real running stack, then triggered a real run through the real gateway API — `SQL` (3/3), `BUSINESS_API` (3/3), and `CROSS_TENANT` (1/1) passed on real, live behavior with zero LLM calls involved, while all 8 cases needing an actual generated answer failed at the same known zero-credit-balance gap as every other phase since Phase 6 (confirmed via each case's own recorded error and the ai-service log), and — the actual point of the retrieval/generation split — `recallAtK` still averaged 1.0 across the cases that computed it, proving retrieval itself is correct independent of the billing gap. Next: Phase 18 — Observability. Spec §27's data model doesn't include a traces/requests table (unlike every other phase's own tables), which settled the scope: this phase is request-id-correlated structured logging along the spec's own trace tree (auth → retrieval → tool calls → LLM request → response), not a new persisted, queryable observability feature with its own admin UI. On the gateway, a new `ObservabilityModule` (`@Global()`, so every feature module gets it without importing it explicitly) provides `RequestContextService` — an `AsyncLocalStorage`-backed store set once per request by a new global `RequestLoggingMiddleware` — and every outbound call to ai-service (RAG, memory, evaluation clients) now forwards the same id as an `X-Request-Id` header. On ai-service, a `contextvars.ContextVar` (`app/core/request_context.py`) plus a `logging.Filter` (`app/core/logging_config.py`) stamp that same id onto every existing `logger.*` call in the codebase automatically — the tool-call logging Phase 11 already had, for instance, needed zero code changes to become request-correlated. New logging was added at exactly the points spec §27 names and nowhere else: retrieval latency + chunk count (`app/rag/service.py`), model/provider/token-usage/duration for every LLM call — one instrumentation point (`create_message`) covers RAG, agent, SQL generation, and memory summarization at once, since they all funnel through it — SQL validation accept/reject outcome (`app/sql/service.py`), and one summary line per evaluation run (`app/evaluation/runner.py`). `JwtAuthGuard` gained a warning log on auth failure specifically, since spec's trace tree names authentication as its own stage and a failure there has no request.user yet for the final access-log line to report. Redaction was satisfied by construction rather than a scrubbing utility: none of these log lines ever touch a request body, an Authorization header, message/document content, or the AI API key — only ids, counts, model names, and durations — so there was nothing to redact out of what already gets logged. Live-verified end to end: triggered a real evaluation run through the real gateway API and grepped both services' logs for the one generated request id — it appeared on the gateway's own access-log line, every ai-service retrieval/LLM-rejection/tool-call/evaluation-summary/access-log line for that run (all 15 cases), correctly correlating a single request across two services and roughly a dozen distinct log lines — and separately confirmed a bad bearer token produces the new `JwtAuthGuard` warning line. Next: Phase 19 — Reliability. Most of spec §28's checklist was already satisfied by earlier phases' proactive design, audited and confirmed rather than rebuilt: idempotent document jobs, RabbitMQ manual acknowledgements, x-death-based bounded retry with a dead-letter queue (all Phase 1/4, see `docs/architecture/rabbitmq-topology.md`), database transactions (`withTransaction`'s BEGIN/COMMIT/ROLLBACK, used pervasively since Phase 8), and timeouts on every external call that already existed — tool calls (Phase 11's per-tool `timeout_seconds` plus `registry.execute()`'s own `asyncio.wait_for`), both ai-service Postgres pools (Phase 1's `command_timeout`), and the SQL role's own `statement_timeout` (Phase 12). One genuine audit finding worth noting explicitly: "circuit-breaker/backoff" for the LLM call was *already* satisfied too, just never stated — the Anthropic SDK retries connection errors/429/5xx with exponential backoff on its own (`max_retries`, default 2) before anything in this codebase ever sees the error; a 400 like the account's own zero-credit-balance rejection is correctly never retried, since it isn't transient. This phase's actual new work: (1) publisher confirms (spec's own explicit gap — nothing before this phase had them) on both RabbitMQ producers in the pipeline: the gateway's `IngestionPublisher` (`createConfirmChannel()`, awaiting the broker's ack before `publishIngestionJob()` resolves — a publish the broker never confirmed now surfaces as exactly the same "mark FAILED, recoverable via reindex" path `DocumentsService` already had, instead of a document silently stuck in PROCESSING forever) and, arguably more important, `services/document-worker`'s own DLQ publish for permanently-failed messages (previously fire-and-forget immediately before acking the original — the one place a lost confirm meant the message vanished with no record anywhere; now the original message is only acked once the DLQ publish is broker-confirmed, left unacked for redelivery otherwise); (2) explicit, intentional timeouts where only an implicit default existed before: `anthropic.AsyncAnthropic` now sets `timeout=60s`/`max_retries=2` explicitly rather than relying on the SDK's own 10-minute default, the gateway's Postgres pool gained `connectionTimeoutMillis`/`statement_timeout`/`query_timeout` (it had none at all), and all three gateway→ai-service HTTP clients (RAG, memory, evaluation) gained an `AbortSignal.timeout()` sized to what each actually does — 120s for the streaming RAG call, 30s for the short memory-summarization call, and a deliberately much larger 300s for the evaluation-run call, which fans out across an entire dataset's cases sequentially and can legitimately take minutes. Live-verified end to end: uploaded a real document through the confirm-channel-backed publish path and watched it reach `READY` with no confirm errors logged, and re-ran the Phase 17 evaluation dataset to confirm the new explicit LLM client timeout/retry settings changed nothing about its already-verified pass rate. Next: Phase 20 — Caching. A new `app/core/cache.py` in `apps/ai-service` is the one place any code builds a cache key or talks to Redis for this purpose — `build_cache_key(organization_id, *parts)` always emits spec's own literal shape (`org:{orgId}:...`), so "do not cache across organizations" holds by construction rather than convention, and `get_cached`/`set_cached` treat any Redis error (or invalid JSON) as a plain cache miss rather than raising — a cache is optional infrastructure, same graceful-degradation posture as Phase 16's conversation-summary fallback. Wired into the three places that are genuinely "safe, repeatable retrieval/analytics results" per spec's own framing: `query_sales` and `calculate_metric` (`app/tools/business_tools.py` — `calculate_metric`'s key literally matches spec's own worked example, `org:{orgId}:analytics:revenue:{from}:{to}`, generalized to whichever metric was asked for), and `run_sales_query` (`app/sql/service.py`). All three are keyed by organization even though mock-business's dataset (Phase 10) is identical across every org today — a deliberate defense-in-depth choice, not something today's data model happens to require. `run_sales_query`'s cache key is the one place spec's "include model/prompt/retrieval version in AI-cache keys when necessary" actually applies: it's keyed on the model name and a new explicit `SQL_PROMPT_VERSION` constant (`app/sql/prompt.py`) alongside the question, so a cache hit skips `generate_sql` — the expensive, billed step — entirely, and changing the model or the SQL-generation prompt can never serve a result generated under different semantics. Deliberately out of scope: RAG retrieval/answer caching. Two reasons, not just one: real chat questions are rarely verbatim-identical (unlike the fixed evaluation dataset), so the hit rate would be low; and "invalidate when source documents change" would need real cross-service coordination (gateway's document upload/delete/reindex would have to signal ai-service) that nothing in this phase's actual scope needs, since nothing here caches anything document-derived — building that invalidation path now, before there's a cache it protects, would be exactly the kind of premature infrastructure the project has avoided in every prior phase's scope calls (Phase 7's RRF-over-reranker, Phase 18's no-new-observability-table). TTLs are explicit everywhere (`cache_ttl_seconds`, 300s default) even though mock-business's seeded dataset never actually changes at runtime — the setting exists for a real backend that would, not because today's demo data needs it. Live-verified end to end: ran the Phase 17 evaluation dataset twice in a row and confirmed, from the ai-service logs, that the second run's `calculate_metric` case (`delayed_order_count`) succeeded with no `GET /orders?status=DELAYED` call to mock-business at all (duration dropped from 3.7ms to 1.2ms) while `get_order`/`get_inventory_status` — not cached — still hit mock-business normally both times; confirmed the exact key and a live counting-down TTL directly in Redis. Spec §33 is just a list of the gateway's public routes plus "keep API contracts versioned and typed" — an audit against that exact list (`apps/gateway/src/**/*.controller.ts`) found 20 of the 21 listed endpoints already existed and matched, but `GET /conversations/:id` was missing entirely (no controller handler, no service method) despite every sibling conversation route existing; added as `ConversationsService.getOne`/`ConversationsController.getOne`, reusing the same tenant-scoped `requireConversation` lookup every other conversation method already used. Making the gateway actually import a workspace package it never had before surfaced a real toolchain gap: `apps/gateway` builds via plain `tsc` with no project references, and having it compile `packages/shared-types`' raw source directly would have pulled a file outside `apps/gateway` into the same `tsc` program, shifting the computed output layout (a classic monorepo `rootDir` pitfall) and breaking `infra/docker/gateway.Dockerfile`'s `CMD ["node", "apps/gateway/dist/main.js"]`. **Known gap (found in Phase 15, and inherent to this kind of defense)**: none of the above can prove Claude itself actually *resists* a live injection attempt — that's a model-behavior question, not a code-structure one, and it's blocked by the same zero-credit-balance gap as every other "does it actually answer well" question in this project. What's verified here is the half that's ours to guarantee regardless of model behavior: the untrusted content is always delimited, labeled, and structurally kept out of anything that looks like an instruction. Real behavioral verification (does the model actually comply or refuse) belongs in Phase 17's evaluation suite once real answers can be generated.

**Resolved design question (from Phase 11's own note)**: whether Phase 12 would replace `query_sales`/`calculate_metric`'s implementation or add something new — resolved by adding `run_sales_query` as a distinct, additional tool. Reasoning: the two Phase 11 tools take structured arguments (a status enum, explicit dates) and are simpler/cheaper when an agent already knows the exact shape of what it wants; `run_sales_query` takes a free-text question and is more flexible but costs an extra LLM round-trip and carries the SQL-injection-shaped risk surface. Having both gives a future agent a choice, matching how the flagship example flow ("choose analytics/SQL tool") implies a choice exists rather than one single hardcoded path.

**Known gap (found in Phase 13, still open after Phase 14)**: nothing in the actual chat flow (`POST /conversations/:id/messages`, Phase 8) calls `/agent/run` yet — the gateway still calls the plain `/rag/query` (or `/rag/query/stream`) endpoint directly, so a real chat conversation still can't use tools at all today; the flagship scenario only runs through the standalone `/agent/run` endpoint. Wiring the agent loop into chat is unaddressed by any phase's stated scope so far — worth deciding explicitly, likely alongside Phase 16 (Conversation Memory) or Phase 25 (Frontend Screens), since a chat UI showing "tool activity" (spec §34) implies the chat path needs to be agent-driven by then. Separately, Phase 12's SQL allowlist is intentionally narrow (one flat table, ~10 functions, no CTEs/joins/window functions) — adequate for the stated aggregate-analytics use case, but a real second table would need real thought about join-graph validation, not just extending the table allowlist.

**Known gap**: `AI_API_KEY` has a valid key configured but the Anthropic account has zero credit balance. Live-verified through `docker compose` end to end: register → login → create conversation → post message (persisted immediately) → open `GET /conversations/:id/stream` and observe real SSE events (`message_start` then `error`) → confirm only the user message was persisted and the conversation was immediately free for a retry. The retrieval pipeline (embed → hybrid search → prompt construction, now including multi-turn history) runs correctly end to end against real documents; the actual Claude answer-generation call still hasn't produced a real answer live, pending billing being set up on the account. One known rough edge from this phase: if a client opens `GET /conversations/:id/stream` only after `POST .../messages` has already returned, an extremely fast failure (like this billing rejection, which fails before any token is streamed) can occasionally finish and evict itself before that GET request lands, returning 404 instead of the `error` event — a real (non-instant) LLM call streams for long enough that this isn't a practical problem, and posting a new message is unaffected either way.

**Known gap (found in Phase 9)**: there is still no way to add a second user to an existing organization through the API. `POST /auth/register` is the only user-creation path, and it always creates a brand-new organization with that user as its sole ADMIN — there's no invite/create-user-in-an-existing-org endpoint anywhere in the spec's API contract (§33 lists only `GET /admin/users` and `PATCH /admin/users/:id`, no `POST`). Phase 9's admin endpoints (list/update/audit) are fully built and live-verified, but were only exercisable end-to-end by seeding a second user directly via SQL — a real deployment currently has no way to grow an org past one user. Worth deciding explicitly (an invite-by-email flow, an admin-issued signup link/code, or an admin-created-user-with-temp-password flow) before this matters for a real demo; not addressed here since it's outside every phase's stated scope so far.
