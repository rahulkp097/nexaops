# Security Checklist

Implements spec §31. Most of this checklist was already satisfied by decisions made in earlier
phases — this file is the audit, cross-referencing exactly where each item is enforced, plus the
two items that were genuinely missing until Phase 22 (security headers, rate limiting).

| # | Item | Where it's enforced |
|---|---|---|
| 1 | Secrets excluded from Git | `.gitignore`: `.env`, `.env.local`, `.cache/`. `git ls-files` contains only `.env.example` (placeholders). |
| 2 | Environment-specific secret management | `ConfigService`/pydantic `Settings` read every secret from the environment, never hardcoded (except local dev fallback defaults in `apps/ai-service/app/core/config.py`). `apps/gateway/src/config/validate-env.ts` (Phase 22) fails at boot with one clear error if `JWT_SECRET`/`JWT_REFRESH_SECRET`/`DATABASE_APP_URL`/`RABBITMQ_URL`/`REDIS_URL` are missing, instead of failing silently the first time each is actually read. |
| 3 | Password hashing | `apps/gateway/src/auth/password.service.ts` — bcrypt, 12 salt rounds. `verify()` swallows compare errors as `false` rather than throwing. |
| 4 | JWT validation | `apps/gateway/src/auth/guards/jwt-auth.guard.ts`, registered globally via `APP_GUARD` in `auth.module.ts`. Bearer-scheme extraction, separate secrets for access vs. refresh tokens. Opt-out only via `@Public()`. |
| 5 | Refresh-token rotation/revocation | `apps/gateway/src/auth/auth.service.ts`. Refresh tokens are SHA-256-hashed before storage (the raw token is never persisted); rotated (old row revoked, new one issued) on every use; **reuse of an already-rotated token revokes every active session for that user** (`security.refresh_token_reused`) — a theft signal, not just a rejected request. Logout is idempotent by design so it can't be used as an oracle for guessing valid tokens. |
| 6 | RBAC | `apps/gateway/src/auth/guards/roles.guard.ts` + `@Roles()`, global via `APP_GUARD`. Authorization has always lived in code, never in an LLM prompt (spec §11/§42) — audited again in Phase 15. |
| 7 | Tenant isolation | `organization_id` filtering in every repository query (gateway) and every retrieval/keyword-search query (ai-service, filtered on both `document_chunks.organization_id` and `documents.organization_id` independently — defense in depth against the two ever drifting apart). `organizationId` always comes from the verified JWT claim, never a request body field. Live cross-tenant-isolation proof: `apps/ai-service/tests/integration/test_retrieval_integration.py` (Phase 21). |
| 8 | Input validation | Gateway: global `ValidationPipe({ whitelist: true, forbidNonWhitelisted: true, transform: true })` (`main.ts`) plus per-field `class-validator` decorators on every DTO. ai-service: every tool/RAG/SQL/evaluation input is a Pydantic model; a tool call with the wrong shape is rejected before its handler ever runs (`app/tools/registry.py`). |
| 9 | CORS allowlist | `main.ts` — `CORS_ORIGINS` env var (comma-separated), `credentials: true`. An explicit allowlist, never `origin: true`/`*`. |
| 10 | Security headers | **New in Phase 22.** `app.use(helmet())` in `main.ts`, applied before every other middleware. This is a pure JSON/SSE API with no HTML rendering of its own, so helmet's default Content-Security-Policy costs nothing; the rest (X-Content-Type-Options, X-Frame-Options, HSTS, a conservative Referrer-Policy) are standard defense-in-depth for any response a browser could be pointed at directly. Live-verified: `curl -sI http://localhost:4000/health` shows all of them. |
| 11 | Rate limiting | **New in Phase 22.** `@nestjs/throttler`, global default (100 req/60s per client) via `ThrottlerModule`/`APP_GUARD` in `app.module.ts`. `auth.controller.ts`'s `register`/`login`/`refresh` — the routes brute-force/credential-stuffing actually target — override it to a tighter 10 req/60s via `@Throttle()`. In-memory storage, adequate for this project's single-gateway-instance deployment (spec §39); a horizontally-scaled deployment would want a shared store instead so every instance enforces the same counter. Live-verified: 15 rapid `/auth/login` attempts returned `401` for the first 10, `429` for the rest. |
| 12 | File-size/type validation | `apps/gateway/src/documents/documents-multer.config.ts` — `fileSize` limit (default 25MB) and a `fileFilter` against an explicit MIME-type allowlist (PDF/DOCX/TXT only), matching `documents.constants.ts` and the `document_status` CHECK constraint in the documents migration. |
| 13 | Safe file storage keys | `documents.constants.ts`'s `buildStorageKey(orgId, documentId, mimeType)` never incorporates the client-supplied filename — the key is derived entirely from server-generated ids and a fixed extension lookup, so path traversal via a crafted filename is structurally impossible, not just filtered. |
| 14 | Read-only SQL credentials | `nexaops_readonly` Postgres role (`infra/database/migrations/..._create-db-roles-and-grants.js`): `default_transaction_read_only = on`, `SELECT`-only default privileges. A dedicated connection pool (`apps/ai-service/app/core/readonly_db.py`) used exclusively by the SQL tool — never shared with the read/write pool. |
| 15 | SQL parser/allowlist | `apps/ai-service/app/sql/validator.py` (Phase 12) — single-statement, `SELECT`-only, table/column/function allowlists, `SELECT *` rejected except inside `COUNT(*)`. Re-serializes from the validated AST, so what executes is provably what was validated, never the model's original text. |
| 16 | Statement timeout | `ALTER ROLE nexaops_readonly SET statement_timeout` at the Postgres level (belt-and-suspenders alongside the readonly pool's own `command_timeout`) — bounded even if the application-layer validator were ever wrong. |
| 17 | Result limits | SQL: a `LIMIT` is force-injected into every validated query regardless of what the model wrote (`sql_row_limit`). Tools: every `ToolDefinition` declares a `max_result_bytes` cap, enforced in `registry.execute()` before a result is ever returned. |
| 18 | Audit logs | `audit_logs` table + `AuditService`, always written inside the same transaction as the event it's recording. Covers registration, login success/failure, token refresh, refresh-token reuse (a theft signal), logout, and document lifecycle events. Readable only by an org's own ADMIN (`GET /admin/audit-logs`), tenant-scoped like everything else. |
| 19 | PII/sensitive-data redaction | Structural, not a scrub-on-the-way-out utility: `apps/gateway/src/observability/request-logging.middleware.ts` and `apps/ai-service/app/api/middleware.py` (Phase 18) log only method/path/status/duration/ids — never a request body or an `Authorization` header. `jwt-auth.guard.ts` logs *that* a token was missing/invalid, never the token itself. One deliberate exception, audited and confirmed intentional rather than a gap: `auth.service.ts`'s `user.login_failed` event stores the submitted email — but only ever scoped to that account's own real organization (looked up from the user record, never the caller-supplied one), so it never crosses a tenant boundary, and it's the same email that org's ADMIN can already see via `GET /admin/users`. Standard failed-login audit-trail practice, not a new exposure. |
| 20 | Prompt-injection defenses | Phase 15: retrieved evidence and tool output are always structurally delimited and explicitly named as data, never instructions, in both the RAG and agent system prompts (`app/rag/prompt.py`, `app/agents/prompt.py`). Adversarial regression tests: `test_prompt_injection_defenses.py`. Live-verified again in Phase 21's E2E script (a document containing the exact worked-example injection sentence ingests normally, is retrieved as inert data). |
| 21 | Tool authorization | `app/tools/registry.py` — every tool declares an explicit `allowed_roles`; `execute()` rejects a disallowed call server-side (`ToolAuthorizationError`), and `to_anthropic_tools(role=...)` never even offers the model a tool name outside its role in the first place. Authorization is never something the model decides. |

## Known gaps (not this phase's scope, tracked here for visibility)

- No invite/create-user-in-existing-org flow yet (`POST /auth/register` always creates a brand-new
  org) — found in Phase 9, still open.
- Chat (`POST /conversations/:id/messages`) still calls the plain RAG pipeline directly, not the
  agent/tool loop — found in Phase 13, still open.
- `ConfigModule`'s `validate` checks presence, not strength — a real `JWT_SECRET` of `"a"` would
  still pass. Worth a minimum-length check if this ever needs to satisfy a compliance audit rather
  than just catching a missing `.env` entry.
